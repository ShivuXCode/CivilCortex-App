# Project Analysis

## 1. One-Sentence Description
CivilCortex is a structural health assessment prototype that pairs a basic building inspection CRUD application with a disconnected LangGraph-based multi-agent AI pipeline for evaluating engineering defects against regulatory standards.

## 2. Problem
Structural engineering triage requires manual evaluation of field defects (cracks, spalling) against massive, complex regulatory standards. This manual process is slow, creates a bottleneck between field inspectors and lead engineers, and leaves room for human error.

## 3. Solution
The project attempts to provide a "Deterministic-Generative Hybrid Architecture" where field images are uploaded and analyzed by computer vision. A multi-agent AI workflow (LangGraph) then determines priority, risk, required resources, and uses Retrieval-Augmented Generation (RAG) against ChromaDB to output a strict, standard-compliant executive maintenance report. 

## 4. Target Users
- **Field Inspectors:** Who capture photos and log defects.
- **Lead Civil Engineers / Stakeholders:** Who review the AI-generated executive summaries and approve maintenance actions.

## 5. Core Features
- User authentication and building hierarchy management (Building -> Floor -> Area -> Element).
- Image upload and defect logging pipeline.
- Backend API built with FastAPI and SQLAlchemy.
- A decoupled 6-stage LangGraph multi-agent AI pipeline using Gemini 1.5/3.6 Flash.
- Local RAG vector store using ChromaDB.

## 6. Technology Stack
- **Frontend:** React 19, TypeScript, Vite, TailwindCSS
- **Backend:** Python 3.10+, FastAPI, Uvicorn, SQLAlchemy
- **Database:** PostgreSQL (via Docker) or SQLite
- **AI/ML:** LangGraph, LangChain, Google Generative AI (Gemini), ChromaDB
- **Infrastructure:** Docker Compose (PostgreSQL, Redis, MinIO)

## 7. Current Status
**Proof of Concept / Mocked Prototype.** 
While the UI and basic database CRUD operations work, the core AI multi-agent workflow is entirely disconnected from the web application, and the computer vision image analysis is completely mocked.

## 8. Biggest Strengths
1. **Architectural Vision:** The 6-stage deterministic-generative LangGraph design is theoretically robust for avoiding LLM hallucinations.
2. **Clean CRUD Implementation:** The FastAPI routing, Pydantic schemas, and SQLAlchemy models are cleanly separated and structured.
3. **Containerized Infrastructure:** The `docker-compose.yml` provides a realistic production-like stack.

## 9. Biggest Weaknesses
1. **Disconnected Core Value:** The LangGraph AI pipeline is not wired into the FastAPI backend or the React frontend; it only runs via CLI test scripts.
2. **Mocked ML Inference:** The `MLService` and `CVPipeline` do not actually run the 21MB `.keras` model; they return hardcoded JSON results.
3. **Incomplete Frontend:** The frontend "New Inspection" flow promises AI analysis but relies on the mocked backend endpoints.

## 10. Biggest Risks
1. **False Sense of Completion:** A stakeholder looking at the frontend UI and the `PROJECT_DOCUMENTATION.md` might assume the AI is fully integrated, which it is not.
2. **Missing Integration Complexity:** Wiring the asynchronous, multi-agent LangGraph workflow into a synchronous REST API endpoint will introduce significant UX and architectural challenges (e.g., WebSockets or polling are needed).
3. **API Rate Limiting:** The LLM nodes rely heavily on external Gemini APIs which will bottleneck a production application if not handled via queues.

## 11. Is the Current Solution Enough?
**NO.**
The current solution is merely a facade over a CRUD application. The primary value proposition—the agentic workflow that analyzes cracks and recommends RAG-backed maintenance—is completely isolated as a CLI script and is not accessible to actual users of the web application.

## 12. Top 10 Recommended Actions
1. **P0:** Wire the LangGraph workflow (`workflow_runner.py`) into the FastAPI `/analyze` endpoint.
2. **P0:** Implement real asynchronous task processing (e.g., Celery or BackgroundTasks) for the LangGraph workflow, as it is too slow for a blocking HTTP request.
3. **P1:** Remove the hardcoded mock responses in `MLService` and implement real inference using the `.keras` model.
4. **P1:** Update the frontend to handle asynchronous AI analysis (loading states, polling, or WebSockets).
5. **P2:** Add frontend views to actually display the detailed executive summary report generated by the LangGraph pipeline.
6. **P2:** Implement proper role-based access control (RBAC) to separate Field Inspectors from Lead Engineers.
7. **P2:** Add unit and integration tests for the FastAPI routes (currently only manual test scripts exist).
8. **P3:** Remove `DEMO_MODE` bypasses from the core AI agents to ensure real API usage is tested.
9. **P3:** Add database indexing to the `defects` and `inspections` tables for scalability.
10. **P3:** Implement proper file storage logic (MinIO integration is in docker-compose but `ImageService` lacks full cloud integration).

# PHASE 3 — PROBLEM STATEMENT

### Problem
Structural defects (cracks, spalling, settlement) must be analyzed in the field and cross-referenced with massive, strict regulatory engineering standards to determine the correct repair procedure.

### Existing situation
Inspectors take photos and write manual notes. Lead engineers later review these notes, manually search through physical or digital regulatory codes, determine the risk, and write a manual repair plan.

### Pain points
- Slow turnaround time between inspection and repair planning.
- High risk of human error or non-compliance with complex regulations.
- Bottleneck at the senior engineer level.

### Why this solution is useful
It automates the regulatory cross-referencing (via RAG) and drafts the executive summary (via LLM) immediately upon photo upload, saving hours of manual engineering review time while theoretically guaranteeing standard compliance.

# PHASE 4 — SOLUTION ANALYSIS

### A. Non-technical explanation
CivilCortex is an app where a field worker snaps a photo of a crack in a wall or tunnel. The app uses AI to instantly identify the crack, figure out how dangerous it is, and then reads through hundreds of pages of engineering rulebooks to write a professional, step-by-step repair guide for the boss to approve.

### B. Technical explanation
The system features a React frontend that uploads images to a FastAPI backend. The image is intended to be parsed by a ResNet-18 CV model to classify the defect. This classification is fed into a 6-node LangGraph StateGraph. The graph deterministically calculates risk and priority, uses ChromaDB to perform a similarity search against a vector-embedded knowledge base of civil regulations (RAG), and prompts a Gemini Flash LLM to synthesize the state into a formatted executive summary.

# PHASE 6 — USER FLOWS

**The Illusionary "Happy Path" (What UI claims vs reality):**
1. User logs in -> `POST /api/auth/login`
2. Navigates to New Inspection -> Selects Building/Floor/Area/Element.
3. Uploads Image -> `POST /api/inspections/{id}/images` (Saves to local disk).
4. Clicks "Analyze Image" -> `POST /api/inspections/{id}/images/{img_id}/analyze`.
   - *Reality:* Backend calls `MLService.analyze_image` which immediately returns a hardcoded dictionary `{"defect_type": "crack", "confidence": 0.85}`.
5. User clicks "Save Observation" -> Creates Defect and Observation in database.
   - *Reality:* The LangGraph pipeline is NEVER triggered. No executive summary is generated. No RAG is performed.

# PHASE 10 — AUTHENTICATION & AUTHORIZATION

- **Mechanism:** OAuth2 with Password Flow (JWT tokens).
- **Implementation:** `app.services.auth_service.py` uses `passlib/bcrypt` for hashing and `PyJWT` for signing.
- **Authorization:** `get_current_user` dependency enforces token validity.
- **Flaws:** IDOR (Insecure Direct Object Reference) is mostly prevented as queries filter by `Building.owner_id == current_user.id`. However, there is no Role-Based Access Control (RBAC). An "Inspector" and a "Lead Engineer" are technically the exact same user entity, meaning anyone can approve or dismiss defects.
